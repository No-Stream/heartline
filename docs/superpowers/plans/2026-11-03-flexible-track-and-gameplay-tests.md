# Flexible track and gameplay tests

> **For agentic workers:** Each work item below becomes one Backlog ticket. Pick one up, write its test-first steps if it needs them, and carry it out with superpowers:subagent-driven-development or superpowers:executing-plans. Items are ordered. Respect the dependencies listed on each.

**Goal:** Let the player build the coasters they imagine, such as a curved lift hill, a 60° lift or a climbing turn, without dead ends. Then prove the whole gameplay loop works the way a player would play it, with tests that would have caught the owner's lift-hill dead end.

**Architecture:** Track pieces stay curve data with entry and exit connector states. The chain lift becomes a placement option on any climbing piece that the model's lift rules allow, instead of four hand-picked lift pieces. Turns get climbing and descending versions generated by the catalog. Testing gets five layers:
- a fast Rust test of builder flexibility over the real construction API;
- long player-journey browser tests in live mode;
- session record and replay;
- a frame-smoothness check on the production build;
- a pruning pass that removes tests the new layers make redundant.

**Tech stack:** Rust (crates/sim, crates/sim-wasm), TypeScript client (web/src), Playwright (web/e2e), Backlog.md tickets.

**Spec:** `docs/superpowers/specs/2026-11-02-theme-park-sim-design.md`, section 3 (coaster construction, what makes each model unique). Related tickets: TASK-31 (curvature continuity), TASK-42 (level-out reachability), TASK-43 (broader vocabularies), TASK-41 (test tiers), TASK-57 (typed worker protocol), TASK-58 (tool interface in main.ts).

## What went wrong

On Timber Tumbler the owner started a chain lift and could not go on. The lead could not reproduce a true dead end. After `LiftLevelToGentleUp`, the palette offers only `GentleUp`, `GentleUpToLevel`, `GentleToSteepUp`, `LiftGentleUpToLevel` and `Lift`. The code confirms the likely cause:

- `crates/sim/src/track/catalog.rs` defines every turn with `Level` entry and exit slopes. There are no sloped turns at all. The one descending helix (`TwisterHelixLeft`) has level ends with a dip in the middle.
- Lift pieces are four hand-made clones (`Lift`, `LiftFlat`, `LiftLevelToGentleUp`, `LiftGentleUpToLevel`). There is no lift version of a steep climb, a slope transition, a vertical curve or a turn.
- `Slope` stops at `UpSteep`, which has gradient 1.0, or 45°. There is no 60° slope.
- The existing reachability test (`every_model_can_return_to_level_from_every_reachable_connector` in `crates/sim/src/track/tests.rs`) only checks that a model can get back to level. It doesn't check that it can turn, keep lifting or do anything a player expects. The browser tests that build coasters follow fixed piece lists in frozen test mode, so none of them ever tried to turn on a lift.

The tests passed because they checked what the code did, not what a player would try.

## Flexible track

### Chain lift as a placement option

Replace the four lift piece ids with a chain toggle in the builder, the same rhythm as RCT2.

- `Construction` gains a `chain: bool` builder mode. When it is on, `append` places the piece with `PieceKind::Lift`, and `choices` refuses pieces that can't carry a chain. The refusal is a new `ConstructionError::ChainNotAllowed`, shown as "No chain lift on this piece".
- Which pieces may carry a chain is a model rule, not a list. A new `LiftRules { max_slope: Slope, curved: bool }` sits on `CoasterModel`, replacing `lift_types: Vec<LiftType>`, which only holds `Chain` today. A piece is eligible when all of these hold:
  - the model has lift rules;
  - the piece has no inversion and a plain shape;
  - both its entry and exit slopes are at least `Level`, and neither is steeper than `max_slope`;
  - it either keeps its heading or `curved` is true.
- Delete `PieceId::Lift`, `LiftFlat`, `LiftLevelToGentleUp` and `LiftGentleUpToLevel`. Their uses become the base piece with the chain on. Known uses: catalog, models, `physics/mod.rs` demo circuit, `facilities.rs` tests, `track/tests.rs`, `physics/tests.rs`, `sim-wasm/src/tests/construction.rs`, `sim-wasm/examples/proximity_runtime_bench.rs`, `web/src/construction-choices.test.ts`, and the e2e specs construction, coaster-boarding, block-sections and wooden-twister. There are no golden state hashes, so changing the enum is safe.
- Physics, block sections and crest confetti already key on `PieceKind::Lift`, not on piece ids (`physics/mod.rs` line ~450 and `track/blocks/mod.rs` line ~275). Curved and steep lifts therefore need no physics change. The lift runs at `PhysicsConfig::lift_speed`. A per-section lift speed setting stays in TASK-43, and the chain-as-kind design makes it straightforward: a section is a run of contiguous lift pieces.

### Climbing and descending turns

Generate slope versions of every turn instead of hand-listing them.

- For each turn base (small and large, flat and banked; entry, continuation, exit and standalone; left and mirrored right), the catalog adds a version for each slope in a global set, starting with `UpGentle` and `DownGentle`. The version has entry and exit slope both set to that slope, and its exit height is the horizontal arc length times the gradient, rounded to the grid.
  - Small turn, 16 m radius: 25.1 m of arc at gradient 0.5 is 12.6 m of rise, which rounds to z = 6, or 12 m.
  - Large turn: rounds to z = 12 or 13. Pick whichever keeps vertical g closest to zero mid-piece.
  - `Piece::at` already rescales height on diagonal headings.
- A slope version keeps its base's `PieceId`. A connector state picks out exactly one version, so the construction lookup changes from "find the template by id" to "find the template by id whose entry matches this end". Do this in `templates()` and in `Construction::validate` and `append`, which currently call `find(|p| p.id == id)`. This keeps the id count and the models' allowed lists from growing by about 64 entries.
- Each model opts in through a style field, `sloped_turn_slopes: Vec<Slope>`. An empty list means turns are level only.
- Curvature continuity (TASK-31) is unchanged. Connectors carry `horizontal_curvature` and `vertical_curvature`. Slope versions keep their base's horizontal curvature at both ends and set vertical curvature to `Straight` at both ends. A climbing turn can therefore follow only a constant-slope piece, never a slope transition or a vertical curve. That matches the current vertical-curve chain. Turning while the slope changes is a later TASK-43 item.
- The existing tests run over every pair of catalog templates, including `joined_pieces_have_matching_position_tangent_roll_and_curvature` and `all_pieces_match_their_end_states_and_have_regular_curves`, so they guard the new versions automatically. Extend `banked_turns_lean_into_their_curves` and the radius-limit test to the slope versions.
- Display names stay static `&str`. The client adds "Climbing" or "Descending" from the piece's slope, so "Small left turn" at `UpGentle` reads "Climbing small left turn".

### 60° slopes

Add `Slope::UpSixty` and `Slope::DownSixty` with gradient tan 60° ≈ 1.73, plus six pieces: `SteepToSixtyUp`, `SixtyUp`, `SixtyToSteepUp` and their descending mirrors.

- A 4-half-tile (8 m) run rising z = 7 (14 m) gives gradient 1.75, about 60.3°. The implementer picks grid values that land within 1° of 60° and keep the transition's peak vertical g at or below about 4 g at 25 m/s.
- Update `slopeOrder` and `slopeLabels` in `web/src/construction-choices.ts`.
- Support generation and clearance work on any curve and need no change. Expect taller drops to raise excitement and intensity through the existing force-based ratings, with no rating code change. `physics/testing.rs` only branches on `Station`.

|---|---|---|---|---|
| Timber Tumbler (hybrid) | gentle up and down, flat and banked | yes, curved | 60° | 60° |
| Velocity Viper (launch) | gentle up and down | yes, curved (Intamin uses chains; TASK-43 AC1) | 60° | 60° |
| Briar Blitz (wooden twister) | gentle up and down, banked preferred | yes, curved | 45° | 45° |

### Palette presentation

- A "Chain lift" toggle sits above the palette, with `aria-pressed` and key H. H is free; C is close and L is the landscape tool. It dispatches a new `InputAction` `{ type: "construction-set-chain", enabled }`, and the worker calls `construction_set_chain`.
- While the toggle is on, pieces that can't carry a chain show as refused with their reason. Placed lift pieces already draw with chain art.
- Group pieces by geometry instead of by name substring. Today `piece_group` in `crates/sim-wasm/src/lib.rs` searches the Debug name for "Turn" and "Up", which would put climbing turns in the wrong group. New rule:
  - inversion: Inversions;
  - heading change: Turns;
  - slope change or constant non-level slope: Slopes;
  - bank change: Banks;
  - station, brakes, launch and terrain pieces: Special;
  - otherwise Straight.
- The turn, slope and bank steppers in `construction-choices.ts` already work on attributes. With climbing turns they offer turns while climbing, with no extra logic.
- Piece icons come from shapes (`piece-icons.ts`), so new pieces get icons automatically. `piece-catalog.spec.ts` already renders and picks every allowed piece at each rotation.

### How this fits TASK-43

Split TASK-43:
- This plan takes AC1 in part (turns, banks and chain lifts on every model) and AC2 in part (lifts up to 60°).
- TASK-43 keeps per-section lift speed, signature elements, unusual-piece marking, manufacturer support styles, turning during slope transitions, and rebuilding the twister helix from climbing and descending banked turns.
- Deriving the full `allowed_pieces` lists from style rules also stays in TASK-43. Slope versions keep the lists from growing, so this plan doesn't need it.

## Testing strategy

### Builder flexibility test (Rust, fast tier)

New module `crates/sim/src/track/construction/flexibility_tests.rs`, declared from `construction/mod.rs` and added to the `make check` test filter in the Makefile. It uses no new crates: a small splitmix generator, reused from `guests/generation.rs` by making it `pub(crate)`.

It has three parts.

1. **Connector exhaustion.** For each model, run a breadth-first search over reachable connector states, reusing `reachable_connector_states` moved from `track/tests.rs`. Assert:
   - every state has at least one continuation;
   - every state returns to level (the TASK-42 property, moved here);
   - the model's style capabilities hold:
     - from every reachable constant `UpGentle` and `DownGentle` state, some piece changes heading without changing slope, when the style allows climbing and descending turns;
     - with the chain on, a heading-changing lift piece is reachable from a climbing state, when `curved` lifts are allowed;
     - a search restricted to chain-eligible pieces reaches the model's maximum lift slope from level;
     - a train can crest: from the top of a lift, a sequence reaches a descending slope.

   The capabilities are written first as a per-model expectations table inside the test. Once the model data exists, that table is replaced by reading the style fields. On today's code, Timber Tumbler fails on climbing turns, curved lift and 60° lift, with one message per missing capability.
2. **Random walks on the real API.** For each model, each world and each station height:
   - worlds: open flat 128×128, the demo world, and a cramped world with a raised wall near the map edge;
   - station heights: 4, 12, 30 and 100 m, matching the builder's 4–100 m range;
   - runs: 8 seeded walks of up to 30 pieces, with the chain toggled at random where allowed.

   At every step, use `Construction::choices`. Assert at least one `Ok`, or that every refused choice has a reason the panel can show (not `Unavailable` alone) and `undo` works. In the open world, require at least one `Ok`.

   Also check cache consistency: the cached `choices` must equal those of a freshly rebuilt `Construction` with the same pieces. That replaces three hand-written cache tests (see pruning). A failure prints model, world, height, seed and the piece list as a Rust array ready to paste into a regression test.
3. **Closure.** In the open world, take each walk's first 12 pieces and run an A* closer over placed end states. The heuristic is grid distance plus heading and slope mismatch, with a budget of 20,000 expansions. It must reach the start connector and `close()` must succeed. Also verify the named journey circuits (see below) close on the journey park from their stations.

**Budget:** at most 5 s in a debug build for `make check`. Setting `FLEXIBILITY_WALKS=256` gives a long run, which `make test` and `make ci` set.

### Player-journey browser tests

Files:

- `web/e2e/journeys/timber-tumbler.journey.spec.ts`, `velocity-viper.journey.spec.ts`, `briar-blitz.journey.spec.ts`, tagged `@journey`.
- `web/e2e/player/driver.ts`: the shared player driver. It grows out of `game-page.ts`, as the browser-code review proposes. Contents:
  - `startPark(page, { park: "new", seed, speed })`;
  - `openTool`;
  - `clickTile` and `dragTiles`, with picking retried across rotations like `clickTerrain` in `coaster-boarding.spec.ts`;
  - `placeStation`;
  - `choosePiece`, which uses the turn, slope and bank steppers by keyboard or mouse, not `data-piece` shortcuts, except where a test is about the palette;
  - `setChain`, `placePiece`, `closeCircuit`, `testRide`, `openRide`;
  - `layPath` and `layQueue`, `placeFacility`;
  - `waitForState(page, predicate, { ticks })`.
- `web/e2e/player/circuits.txt`: named circuits, one piece per line, with `+chain` and `-chain` lines. The Playwright driver and the Rust closure test both read it, so the circuits can't drift. The Rust side uses `include_str!`, so no serde is needed.
- `web/e2e/player/state.ts`: read-only helpers over `gameTest`, such as `revenue()`, `tickCount()`, `queuedGuests()`, `riders()`.

Rules for journeys:
- Live mode, no `?test`.
- Every action is real mouse or keyboard input through the visible UI.
- `gameTest` is used only to read state (`project`, `pick` for targeting, `paths`, `guests`, `riders`, `testingReport`, `facilities`, tick count) and to `setCamera`. Never `advanceTicks` or `setSurface`.
- No screenshots in journeys.

Each journey runs the whole loop:
1. Open a new park with the entrance only.
2. Lay a path from the entrance.
3. Place food, drink and a restroom.
4. Choose the model.
5. Place the station, with the Landscape tool raising ground for access if the station height needs it, as `coaster-boarding.spec.ts` does today.
6. Build a full circuit back to the station:
   - Timber Tumbler: curved lift, then a 60° lift section, crest, drop, banked turns, an airtime hill.
   - Velocity Viper: keyboard-only building, two launches, a climbing turn, and a slope-stepper level-out (replacing the Velocity Viper slope-to-level spec).
   - Briar Blitz: curved gentle lift, descending banked turns, twister pieces.
7. Close, test, and read the testing report: ratings present, no stall note.
8. Set a ticket price, lay the queue and exit paths, and open the ride.
9. Wait until guests queue, ride and pay: coaster riders seen, park revenue above its value before opening, coaster income above zero.
10. Click a rider and see the guest panel, then wait for the ride memory. This is kept from `coaster-boarding.spec.ts`.
11. Check that crest confetti fired on the curved lift, via `crestBursts()`.

Determinism in live mode:
- The worker gets its configuration from URL parameters through an `init` message instead of its name, matching the browser review and TASK-57:
  - `?seed=` (default 2026, the current hard-coded seed);
  - `?park=new|demo`, where `new` is an entrance, a two-tile path stub and flat land, with no demo coaster or facilities;
  - `?speed=1..16`, which scales ticks per wakeup so journeys run at about ×8.
- The simulation is already deterministic for a seed and command sequence. In live mode only the tick at which each command lands varies. So journeys assert outcomes, not exact values.
- Waits are measured in simulation ticks, never milliseconds. `waitForState` polls a `gameTest` read and fails once the game has advanced N ticks without the predicate becoming true, so slow CI hardware doesn't cause failures. Tick budgets are three times the measured value.
- Each journey records its session (next layer). On failure it attaches the session file to the Playwright report, so a flaky failure becomes a replayable regression.

Playwright gets projects in `playwright.config.ts`:
- `feature`: current specs, frozen mode, 4 workers.
- `journey`: `@journey`, live mode, 2 workers, 1280×720.
- `smoothness`: one worker, small viewport.

### Session record and replay

Record two streams:

1. **Worker command journal.** The authoritative stream. The worker stamps every command it applies with `tick_count()` at the moment it applies it, keeps them in memory with a cap of 100,000, and records `state_hash()` (already exported in `sim-wasm/src/reports.rs`) every 300 ticks. This stream is complete even though facility, path and scenery panels bypass `dispatch` today (`main.ts` lines ~150–215).
2. **Input action log.** Each `InputAction` through `dispatch` with `performance.now()`, the current tick, the viewport and the starting camera. Used for interface-level replay and diagnosis. It becomes complete once TASK-58 routes every panel through `dispatch`.

Export control: an "Export session" button in the Watch bar beside the day clock, with a key binding. It downloads `session-<date>-<time>.json` containing:
- format and version;
- build id (`import.meta.env` plus git hash via Vite `define`);
- seed, park, guest count;
- the command journal;
- the input log;
- hash checkpoints;
- the final tick;
- an optional `expect` block.

Replay harness: `web/e2e/replay.spec.ts` runs every file in `web/e2e/sessions/`.
- It boots frozen with the file's seed and park, posts each command at its recorded tick, and advances ticks between commands. This layer may use a replay hook; the no-actions rule applies to journeys only.
- It asserts no page or worker errors and the file's `expect` block, for example `{ "constructionClosed": true, "ridersAtLeast": 1, "revenueAbove": 0 }`.
- A checkpoint hash mismatch is reported as an annotation pointing at the first diverging checkpoint. It fails the test only when the file sets `"strict": true`, because intentional simulation changes alter hashes. `npm run sessions:rehash` refreshes stored hashes after review.
- Interface-level input replay comes later, after TASK-58.
- A native Rust replay in `sim-wasm` tests is a follow-up. It needs the worker's command application moved into Rust, which fits TASK-57.

### Frame smoothness check

`web/e2e/smoothness.spec.ts`, tagged `@slow`, runs against the preview server, which already serves the production build.

- It loads the demo park live at 960×540, warms up 3 s, then measures 10 s.
- A read-only hook, `?frameLog=1`, records `{ now, tickCount, interpolation, trainX, trainY, trainZ }` from the values `main.ts` actually rendered each frame, plus snapshot arrival times. This tests the real interpolation code, unlike `scratch-stutter.spec.ts`, which reimplements it.

Initial thresholds, to be tuned with the stutter diagnosis:
- snapshot interval p95 at most 50 ms, maximum at most 120 ms (one tick is 33 ms);
- the train never moves backwards between frames, except at the lap wrap;
- displacement per millisecond over sliding 0.5 s windows has a coefficient of variation at most 0.25;
- no frame shows zero displacement while the median speed is above 1 m/s;
- at most 2 long animation frames over 50 ms.

Normalising movement by frame time keeps the check from failing just because software WebGL renders slowly. Land it with or right after the stutter fix. If it lands earlier, mark it `test.fixme` with the stutter ticket id.

## Pruning

Criteria:
- Delete a browser spec when a journey reaches the same user-visible outcome through the same UI. Move any assertion it has that no journey makes into the journey or into a Rust test.
- Delete unit tests that restate data or implementation, such as a constant's value or a train's car count.
- Merge tests of one property across models into one table-driven test.
- Delete bridge tests that duplicate `sim::park` tests now that TASK-54 moved the park into `sim`.
- Keep determinism, thread-count, state-hash, physics, curvature, clearance and support guards, and rendering depth, picking and screenshot guards.

Before deleting a test said to be covered, the implementer reintroduces the bug it guards locally and confirms a remaining test fails.

## Risks

- **Flaky live journeys.** Live journeys may flake under CPU contention. Tick-based waits, two workers and attached sessions limit this. If one flakes twice, replay its session before raising budgets.
- **Grid rounding on climbing turns.** Rounding the rise to the grid makes the average gradient slightly off the connector gradient, which adds small vertical bumps. Item 6's g limit guards this.
- **Slower `choices()`.** More templates slow `choices()`, which validates supports for each one. Item 6 measures it, and cached validation by geometry already exists.
- **Many call sites.** Removing the lift ids touches many tests at once. Item 5 owns all of them in one change.
- **Brittle hashes.** Hash checkpoints change on every intentional simulation change. That is why they are advisory unless a session sets `strict`.
- **Software WebGL timing.** Software WebGL frame timing is irregular. The smoothness thresholds normalise by frame time and need tuning against the real fix.

## Owner decisions (2026-11-03)

- **Chain lift:** a toggle, as proposed.
- **Lift rules:** the proposed model table stands. Timber Tumbler gets curved lifts up to 60°. Velocity Viper gets chain lifts too, curved and up to 60°. Briar Blitz gets curved lifts up to 45°. All three get climbing and descending turns.
- **Paying:** support both ways to charge, each adjustable by the player. Guests can pay at the park gate (an entrance fee, which `ParkFacilities::set_price` currently refuses for the entrance) and per ride (a coaster ticket price). Work item 4 covers both. A park may use either or both, and the journeys check that income rises under each setting.
- **Game speed:** a real player control (×1, ×2, ×4, and a faster test setting if needed) in the Watch bar. Journeys use the same control rather than a test-only `?speed`. Work item 2 builds it.
- **Riders on moving trains:** players do not need to click guests riding a moving train; clicking a train selects the ride. Journeys select a rider while they queue or board and follow that guest. (Decided later on 2026-11-03.)
