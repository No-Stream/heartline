# Test pruning proposal for TASK-75 and TASK-76

This is a proposal only. I did not edit, disable, or delete any test. The plan's deletion check requires reintroducing the guarded bug locally and proving a remaining test fails; that destructive-to-evidence step belongs after the owner approves a specific deletion. The comparisons below identify likely coverage overlap and also call out where the plan no longer matches today's suite.

## Timing and estimated savings

| Tier | Current run | Proposed saving | Basis and limits |
|---|---|---:|---|
| Browser | `npm run e2e -- --grep @slow --workers=2`: 16 passed in 4:41.30 wall time. | About 1 minute wall time (roughly 20–25%). | The five proposed slow-test folds below accounted for 123.7 seconds of individual test time in this run. Two workers overlap that time, and the longest remaining tests still dominate, so this is not a promise of 123.7 seconds off the wall clock. Retaining the closed-coaster test's report and overlay checks would reduce the saving further. |
| Rust | Covered by the successful `make check` selection; no separate full Rust suite run. | Under 1 second in `make check`; not measured. | The `make check` filter includes the proposed closed-circuit construction test and cache tests, but does not include the standalone `track/tests.rs` module. Folding three small filter tests into one table test should save little. |
| sim-wasm | Not run separately. | Under 2 seconds; not measured. | The two proposed duplicate work-budget tests are only part of the 108-test sim-wasm library suite. The plan's roughly 46-second baseline predates today's suite; I did not rerun it. |
| TypeScript | `npm test` passed all 257 tests in 1.65 seconds during `make check`. | Under 0.1 seconds; not measured. | At most one small name-formatting test would fold into existing browser journeys. The remaining construction-choice, unit, and colour assertions are distinct guards. |

`make check` was run once and passed. It reported 185 Rust tests, 257 application tests, 9 art tests, a successful typecheck, and 19 `@fast` browser tests. Its browser phase reported 1.7 minutes. The Makefile runner did not print a single total wall time, and this worktree had to compile Rust and WebAssembly build artifacts during the run, so this was not a warm-build timing. I am not presenting an inferred total as a measured warm time or rerunning the command, per the one-run limit.

The slow run also passed `smoothness.spec.ts`: 604 frames were recorded, with 43.5 ms maximum worker-send interval and no backwards or zero-displacement frames. Its scenario took 15.7 seconds. These are single-run observations, not flake-rate evidence.
